## 2. 三个层级的需求来源

### 2.1 原始Proposal保留的核心

原始问题是 Initial Client Consultation：减少设计师反复收集基础信息的工作，同时避免客户原话在交接中丢失。Proposal明确了多模态输入、结构化需求、可支持的场景编辑、修订记录、Designer Dashboard和Reviewer Agent；还要求区分来源、用户确认、AI假设与未解决问题。它最初以单房间样例验证，并把生成图像定义为辅助说明而非几何事实。[S01]

### 2.2 仓库Spec v0.2已经作出的选择

当前服务器Spec指定OpenPlan3D、自托管受控分支、React/assistant-ui外壳、Pi Agent Core、同源iframe类型化桥接；取消产品内AI生图，仅保留参考媒体理解和真实场景截图。正式几何与业务sidecar由后端统一提交，AI提议不能自行采用，用户目标尺寸不能自动拉伸墙体。[S04,S08]

### 2.3 本次变更与仍待确认的细节

已确定的是全屋范围、家具修改、用途改变、非承重墙拆改与WASD移动。尚未确定的是任意图片自动重建的成功边界、复式楼层、任意第三方资产、完整贴图替换、墙体核实角色、触屏漫游等级和实施日历。本文将这些列为确认项，而不擅自缩回单房间，也不把未确认增强当作已承诺能力。[S03]

本次生成的36张UI参考图属于设计沟通资产，不意味着将AI生图重新加入产品。所有图片都标记为目标界面或示意；面积、预算、家具尺寸、状态和房屋分类示例不构成实测或工程结论。

## 4. 现有架构的真实基础

### 前端与3D

外层为React＋TypeScript＋Vite，咨询采用assistant-ui；工作台通过受控同源iframe嵌入SvelteKit＋Three.js的OpenPlan3D。桥接的load/snapshot/select/update/focus/mode/camera/keyboard等方法是项目适配层，不是上游现成React SDK。父子校验origin、source、project与请求；场景内存可以是草稿，服务端提交后才成为正式值。[S08]

### 后端与数据

实际后端为Fastify＋TypeScript，Pi Agent用于模型与受限工具。Store使用PGlite，项目主要保存于JSONB，另有commands、events、sessions和attachments表。原始规划中的独立PostgreSQL服务、S3附件存储、Docker Compose不能当成当前已经落地的设施。扩围先延用已验证路径，再按数据量决定迁移，不为“技术清单齐全”而提前重构。[S07,S14]

### 几何与业务关联

原生单位为厘米，右栏需求以米等单位展示。当前业务RoomInfo保留wall_ids、几何宽深高和bbox；当前样例是480×400cm客厅与320×360cm房间2，且doors/windows为空。其房间归属逻辑使用bbox，在全屋凹多边形、开放空间、共墙和分割/合并场景下需要升级。[S07,S09,S10]

### 审计基础

已有expected_version、request_id、事务内revision/outbox和SSE同步，有防冲突、幂等和明确采用语义。现有revision字段主要是操作者、类型、时间、请求与版本，不足以直接提供完整before/after选择性撤销。不能把“有revision数组”视为旧ticket12已实现。[S05,S07]

## 6. 必须优先消除的技术风险

**P0：墙体编辑不能通过删掉后端保护来完成。** `syncRoomGeometry`目前拒绝删除/重建边界；正确演进是新增已授权、带依据、带影响清单的墙体命令与拓扑迁移。未知/承重/受保护构件不能被一句自然语言请求自动变成可拆。专业核实也不等于本产品授予施工许可。[S01,S10,S11]

**P0：全屋稳定ID与空间归属。** 上游房间识别会生成新ID，并用墙集合保留部分元数据；拓扑改变后不能直接把新列表替换旧room。必须保存合并/拆分关系，区分几何空间与功能zone，显式迁移需求和家具关联。[S07,S11]

**P0：旧“安全拒绝”需升级为受控能力。** 已采用参考跨房间移动当前会409拒绝，这是原范围的数据保护。增加新transfer命令需要同时迁移需求与房间绑定，并保留历史；不能简单去掉校验。[S09]

**P1：键位、焦点与模式状态。** WASD必须改为位置控制，鼠标负责视角；打开聊天、输入法、弹窗、失焦、退出指针锁时清空按键与速度。父外壳与引擎的模式要由真实事件同步，不能一个显示漫游而另一个已退出。[S08,S11]

**P1：发布不能直接重启dirty工作目录。** 最新交接已准备独立冻结版本，待宿主批准执行。代码回滚优先切换完整旧版本与兼容当前数据，不能把旧数据库覆盖到新写入。已撤回的`deploy-week2.py`草稿不是可执行发布入口。[S04,S13]

## 8. 操作与交接流程

### 8.1 新会话恢复

使用AWS Machine，workdir为`renovation-consultation`，真实项目根为`/home/ubuntu/aws-hackthon/renovation-consultation`。先读AGENTS、CURRENT、README固定映射、Spec、PLAN、tracker，再读目标票及直接依赖与证据。检查HEAD/dirty、实际可用命令和服务；CURRENT是恢复索引，代码与单票证据才是完成事实。[S04,S13]

### 8.2 产品实施

明确本轮目标、范围、基线、受保护改动和验证计划。获得相应实施授权后才更新目标票；按纵向切片完成UI/API/数据/测试。Agent只能提议，用户明确采用后调用统一命令。涉及结构策略、跨房间迁移或导入的写入都不能绕过同一服务端校验。失败保持最后提交值与可恢复草稿。

### 8.3 验证与委派

已有命令包括`npm run check`、`npm test`、`npm run build:web`、`npm run build:engine`和`npm run test:browser`。这些命令存在于已读package，不代表本轮已执行。浏览器仅使用4175与独立合成数据，构建到隔离目录；不在运行服务下重建被其读取的哈希资源。重型检查串行，保留失败记录，不用降低断言或force-click制造通过。[S06,S13]

授权Codex验收后使用`python3 scripts/codex_acceptance.py run`，先验证当前MCP实际可用CLI；该包装器当前默认仍为Week1范围，不能冒充全屋套件。每轮新run ID，回读指纹、退出码、事件、报告、日志和截图；ready_for_review不等于ticket done。不得读取宿主凭据或绕过被拒绝操作。[S13]

### 8.4 发布与恢复

保持4173统一入口与/todo；不要用默认4174预览共享生产.data。最新发布包已准备但未安装，宿主权限批准与具体HOST-ACTION-PLAN是下一门禁。真正切换前重新检查源码/资源封印、服务身份、维护/排空、停止写者后的完整备份和独立检验副本；切换后核对公共资源、会话和内容连续性。只有实际完成才更新发布状态。[S04,S13]

### 8.5 下次接手应拿到什么

本包可作为上下文说明，但不会自动替代服务器权威Spec。完成设计确认后，应在获授权的文档更新中保存v0.3范围变更、增量ticket映射和短CURRENT索引，保留旧验收。每次交接记录目标、状态、文件、HEAD/指纹、运行证据、未测项、服务入口、下一动作与回滚边界。不得把本次36张参考图的设计批准当成产品测试通过。
