# ROOMNOTE 全屋版：细化实施计划

**版本：v0.3-planning / 2026-09-14 / 待设计确认与实施授权**

## 1. 成功状态：交付一套可追溯的全屋方案

用户进入一套完整住宅：左侧围绕全屋/房间/对象咨询，中央可在2D、鸟瞰和第一人称间切换，右侧显示同步的需求、来源与待决策。用户选家具可改款式、位置、尺寸和受支持外观；将次卧改作书房时看到保留项和增删改布局；对符合策略的非承重隔墙先核实分类，再预览门窗与房间影响。每次采用产生可撤销、可追溯的新版本，最终交付同版本的可编辑模型和设计需求书。[S01–S03]

这里有三种不同“完成”：**设计确认**表示同意本图的行为；**代码验收**表示功能在冻结测试与证据中通过；**生产发布**表示指定版本已切换且线上/数据连续性检查通过。三者不得互相替代。

## 3. 数据和一致性设计

### 3.1 现有事实与拟新增模型

现有Store、Scene原生快照、requirements/evidence/commands/events和版本保护应继续复用，不另造一个前端事实来源。以下为**拟新增契约**，并非现成API或数据库迁移。[S07–S11]

| 实体 | 必要字段/关系 | 约束 |
|---|---|---|
| Project | id、schema_version、project_version、scene_version、brief_version、members | 身份由服务端验证；先兼容原版本，再考虑拆分存储 |
| Space | id、floor_id、polygon、boundary_segments、openings、derived_area、status | 几何空间；面积由多边形生成，不用bbox面积冒充 |
| Zone | id、space_id、name、purpose、evidence_ids | 开放客餐厅可共享一个空间而保留两个用途区 |
| SpaceLineage | old/new space_ids、merge/split、revision_id、allocation_decisions | 拆合改变身份时保留关联，不靠名称或最近质心盲猜 |
| WallPolicy | wall_id、unknown/non_load_bearing/load_bearing、protected、evidence、reviewer、time | 缺分类默认为unknown；标记不等于施工许可 |
| Opening | id、wall_id、position、width、height、type、dependencies | 门窗不能因删墙悄悄级联消失；逐项迁移或明确删除 |
| FurnitureInstance | stable logical id、asset_id/version、space/zone、transform、dimensions、capabilities | 替换资产与删除逻辑对象分开；迁移保留历史 |
| Proposal | base_version、typed operations、scope、affected IDs、evidence、status | Agent只能propose；用户明确采用；批量原子提交 |
| Revision | actor/time/request、before/after、target_ids、evidence_ids、compensates | 新撤销是补偿，不删除历史；历史快照只读 |
| ExportManifest | project/schema/engine/asset版本、file hashes、privacy selection | 模型/sidecar/PDF绑定同一快照，导入重新验证权限 |

避免把全部信息无控制地堆入单个Project JSON后无限增长。当前先按旧存储保持兼容，增加有界证据引用与快照策略；是否将附件移到私有对象存储、把审计拆表，应通过项目大小/响应量/备份时间实测决定。S3和独立PostgreSQL在旧文档中只是规划，不直接作为完成基础。[S07,S14]

### 3.2 命令执行链

用户输入/拖拽 → 解析明确scope → 读取服务端快照 → 生成受限操作提案 → 验证能力/墙体策略/几何 → 展示前后差异与影响对象 → 用户确认 → 校验权限、expected_version、request_id → 事务提交几何＋sidecar＋revision＋outbox → SSE同步三栏 → 标记已保存。

预览只存在草稿层。任何解析、资产加载、策略、校验、事务或网络失败都不能改变最后提交值。409应展示本地/远端差异并重新确认，不自动把旧操作套到新版本。幂等重试沿用同一request_id；用户修订请求内容后必须生成新请求。查看相机、选择和面板不写设计revision。

### 3.3 建议的受限操作类型

以下是**项目待实现的类型名**，不是上游API：`furniture.transform`、`furniture.replace_asset`、`furniture.add`、`furniture.remove`、`furniture.transfer`、`room.set_purpose`、`layout.apply_group`、`wall.propose_change`、`wall.apply_change`、`space.reconcile`、`revision.compensate`。操作载荷必须可用共享schema校验，不允许Agent任意脚本、任意URL资产或任意场景JSON绕过策略。

现有`scene/save`仍可作为受控提交入口，但必须增加服务器生成的差异分析与全局策略校验。不能因新增专用墙体API，就留下通用保存、2D快捷键或重新导入可绕过限制的后门。

## 4. 重点能力的实现逻辑

### 4.1 从“双房间”到全屋，不先依赖万能识图

先以有授权的全屋fixture验证几何/对象/门窗/用途/导航闭环。导入按三档：原生可编辑包；受控模板；图片/PDF底图＋比例尺＋人工描边/纠正。AI识别若加入，仅生成候选墙/门/房间和不确定性，再经确认。原图面积与文字不自动成为实测值；用户目标尺寸保持独立。[S01,S02,S07]

同一房屋可以分多个功能zone，但共享墙只应有统一几何身份。房间归属用真实多边形与显式业务绑定交叉验证，而不是多个bbox同时包含对象。门洞是导航连通依据之一，开放口必须表达在模型中。多楼层/楼梯另行冻结用例，不将“全屋”未经确认扩大为任意建筑。

### 4.2 家具的六类正式操作

属性编辑延用旧06能力；移动/旋转新增transform命令；替换更新资产而保留逻辑对象身份；新增可以先作为未采用参考；删除保留退役记录与原证据；跨房间转移原子迁移空间归属与关联家具需求。每类都有单对象和组操作的可见scope，保留/锁定项不能被Agent静默改动。[S09]

资产需记录许可、原始单位、真实包围体、锚点与可编辑材质槽。尺寸缩放与不支持材质必须如实禁用。未加载完成时用明确占位而非宣称最终模型；加载失败不得写入“已替换”。外观质量通过冻结机位/灯光的真实引擎截图验收，文档生成图只用于风格讨论。[S01,S06]

### 4.3 用途变更：两次确认而非一个模糊按钮

例：“次卧改为书房兼客房，保留衣柜。”第一步只修改正式用途需求。第二步生成保留衣柜、移除原床/采用沙发床、新增书桌/书架、通行约束等提案，列出对象与尺寸；取消不改正式场景，采用整组再事务提交。厨卫或涉及结构/水电的用途变更必须显示待专业核实，不以渲染画面宣称实际可行。[S01,S03,S08]

### 4.4 墙体：策略、几何和业务迁移三层分开

第一层是准入：结构分类、受保护标记、来源、专业角色和依据。第二层是几何：端点、连接关系、厚度/高度、门窗附着和闭合多边形。第三层是业务：哪些空间合并/拆分、用途和预算如何保留、家具和需求如何迁移、报告/导航如何过期或重算。[S01,S10,S11]

默认禁止承重、未知和受保护构件的正式拆改。核实非承重也不能被自动描述为可施工，因为其他专业约束和地域要求未在资料中确认。可记录用户改造意愿和讨论预览，但正式场景和交付都必须保留状态。房屋地域、审批和专业核实流程需后续指定，不将用户所在地当房屋所在地。[S01,S03]

尤其注意上游`removeWall`会移除该墙关联门窗；适配层必须先展示门窗清单与选择，统一事务再调用等价变更，不能先发生删除后补业务记录。拓扑变化产生的空间谱系保留旧证据；用途冲突进入待决策，不能随机沿用其中一个房名。[S11]

### 4.5 漫游：输入与通行都要验，不只测模式开关

桌面目标键位为W前进、S后退、A左横移、D右横移；鼠标yaw/pitch。`KeyboardEvent.code`用于物理键位，但UI提示应考虑非QWERTY布局；无设备或浏览器能力时提供明确替代。Pointer Lock须处理用户手势、实际锁定状态与拒绝结果，不能假定iframe桥接的异步mode命令必然获得锁定。[S11,W01,W02]

现有运动控制能复用时间积分、部分失焦清理和原生相机，但必须改变旧WASD转向映射；Three.js的前进/横移方法只处理视点移动，墙体/家具碰撞另行实现。默认设置提案为眼高160cm、速度120cm/s、俯仰±85°、正常地面行走，这些是待验证的UX参数，非空间安全阈值。[S11,W03]

输入状态机建议`orbit → walk_ready → walk_active → walk_paused`；按键松开、Esc、弹窗、focusin、blur、visibilitychange、pointerlockchange、组件销毁都要清空移动量。外壳与引擎通过camera_mode/lock_state事件同步。反复进入不累积监听器；摄像机姿态无需不断发后端revision。[S08,S11]

导航使用地面可行走区域与墙/家具简化碰撞体，每步sweep或短子步减少高速穿透，开门洞可通过，撞墙可滑动，入场点有空间合法性检查。导航碰撞不是结构认证，设计诊断也不是实时导航引擎。墙体/家具采用新版本后重算导航；旧位置失效则提示返回合法点而非把人困进墙里。

### 4.6 全屋Agent和多模态

全屋默认偏好、房间覆盖、对象操作层次分开。“全屋浅色但儿童房彩色”应生成明确排除范围；含糊目标先澄清。工具仅提交候选，采用动作保留真实用户授权。图片可以只标喜欢某区域，音频保留原转写与纠正，视频证据带时间点；外链不支持时明确回退上传。保留旧15视频目标，不悄悄删项。[S01,S05,S06]

### 4.7 交付与恢复

导出使用同一已提交版本生成原生JSON、业务sidecar、真实3D截图、五部分PDF Brief和manifest。预检要验证所有ID、引用、资产与版本；在隔离新项目回读并继续修改/保存后，才能认定可编辑交付。文件中仍保留未测尺寸、未知墙体和未决问题；不是施工图或工程批准。[S01,S05]

旧Week2生产发布是一条独立运维线，可在批准后先发布已验收范围，不等待所有全屋功能；也不能因全屋计划确认就自动获得宿主机权限。[S04]

### 7.2 验收顺序

静态类型与共享schema → 定向逻辑/事务 → 隔离前后端/引擎构建 → 核心浏览器 → 真实provider浏览器 → 视觉/普通点击/设备 → 可编辑导入导出 → 独立审查与全量回归 → 单独批准后的发布与恢复。重型浏览器与模型串行，结果绑定同一源码/构建指纹。修复后新run；保留旧失败，不覆盖日志或截图。[S06,S13]

已有npm命令可沿用，但新全屋测试文件、夹具和脚本必须在实现中创建后才能写进可执行验收命令。不得把计划中的`test:whole-home`之类名字写成仓库已有命令。Codex包装器仍是旧Week1范围，扩展必须显式更新范围与回执契约后再用。

### 7.3 指标迁移

原Proposal提出：5案例中需求正确完整度≥90%；已确认需求和已应用编辑可追溯率100%；20个受支持编辑≥90%成功。这些是**拟定指标，基线未建立**。全屋版建议仍用5个冻结案例，但包含跨房间、用途和非承重墙关联任务；20个编辑要均匀覆盖新增操作，而非重复改颜色。[S01]

安全/一致性闸门不按90%放行：越权、承重/未知墙保护、原子性、幂等、冲突保护、证据保留必须全部通过。视觉与性能单独报告。建议指定目标桌面/手机后设桌面中位60fps、手机中位30fps等体验目标，记录分位数、机型、场景规模与加载条件；目前没有该项目的有效设备基线，不能承诺已达到。
